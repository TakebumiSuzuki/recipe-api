# SQL SAVEPOINT の基礎とトランザクションライフサイクル - 学習ノート

## 1. SAVEPOINT とは？

**SAVEPOINT（セーブポイント）** は、すでに開始されているトランザクションの内部に打つことができる**「しおり（チェックポイント・目印）」**です。

### 名前の由来
ゲームのセーブポイントと全く同じ概念です。
* **ゲーム**: ボス戦の直前にセーブポイントを作っておけば、負けてゲームオーバーになっても最初からやり直す必要はなく、**直前のセーブポイントまで巻き戻してリトライ**できる。
* **データベース**: 長いトランザクションの途中に `SAVEPOINT 目印名` を打っておけば、途中でエラーが起きても全体を破棄せず、**その目印の地点まで部分的に巻き戻す（部分ロールバック）**ことができる。

---

## 2. SQL に導入されたそもそもの背景と経緯

標準SQL（SQL99）で規格化された機能ですが、導入の背景には従来のトランザクション仕様が抱えていた「硬さ」がありました。

### 従来のトランザクションの限界（All or Nothing の壁）
データベースのトランザクションは本来「**ACID特性**」に基づき、**「すべて成功（COMMIT）か、すべて失敗（ROLLBACK）か」** の二者択一（All or Nothing）です。

しかし、実際の業務システムではこの厳密さが不便になるケースがありました：
* **大規模バッチ処理の例**:
  * 10,000件のデータを1件ずつループ処理して登録している最中、**9,999件目で1件だけ不正データがありエラーになった**とする。
  * SAVEPOINT がない場合：トランザクション全体がロールバックされるため、**正常に処理が終わっていた最初の9,998件も道連れで消滅**し、何時間もの処理が最初からやり直しになる。

このような「一部の失敗のために、それまでの正常な処理まで全て捨てるのはコストが高すぎる」という現場の切実な課題を解決するために、**トランザクションを壊さずに途中まで巻き戻せる「部分ロールバック（Partial Rollback）」** として SAVEPOINT が導入されました。

---

## 3. 本来想定されていたユースケース

SQLの仕様として想定されていた主な用途は以下の通りです。

1. **エラーリカバリとリトライ**
   * 処理の直前にセーブポイントを打ち、エラーが発生したらセーブポイントまで巻き戻して別のアプローチを試す。
2. **一部スキップによるバッチ継続**
   * エラーが起きた1件だけをセーブポイントまで巻き戻して破棄・エラーログ出力し、残りの正常なレコードの処理をそのまま続行して最後に一括コミットする。
3. **複雑なビジネスロジックの分岐**
   * ネストしたサブルーチンや関数ごとに安全圏を確保しながら処理を進める。

## 4. 技術的な仕組み（要点）

### (1) 「実コミット」vs「論理コミット（セーブポイント）」
セーブポイントを打つ、またはセーブポイントを確定（`RELEASE SAVEPOINT`）した状態は、**「論理コミット」** と呼ぶのが最も直感的です。

* **処理を行っている本人から見た状態（論理コミット）**:
  * 直前に書き込んだデータを使って次の SELECT や UPDATE が正常に行えるため、まるでコミットが完了したかのように振る舞える。
* **データベース全体から見た状態（実コミットではない）**:
  * ディスクに本確定（永続化）されたわけではない。
  * 外側の親トランザクションが生きているため、いつでも全てをキャンセルできる状態が維持されている。

### (2) 本コミット（実コミット）との3つの決定的な違い

| 観点 | 実コミット (`COMMIT`) | セーブポイント (`SAVEPOINT`) |
| :--- | :--- | :--- |
| **他者への公開（可視性）** | **全員に見える**（公開される） | **自分にしか見えない**（他者からは存在しない扱い） |
| **耐久性（電源断への耐性）** | ディスクに完全書き込みされ、電源が落ちても残る | メモリ/一時領域にあるため、電源が落ちれば消滅する |
| **行・テーブルのロック** | ロックが解放され、他者が編集可能になる | 作業中のため、ロックを保持し続ける |

### (3) DB内部の仕組み（WAL と MVCC の役割分担）
セーブポイントやロールバックが高速かつ安全に動く背景には、データベースの2大機構がタッグを組んでいます。

* **WAL（Write-Ahead Logging: 作業日誌）**:
  * 停電・障害回復のための仕組み。「何をしたか」「どこにセーブポイントを打ったか」が時系列のログとして記録される。
  * ロールバック命令が来た際、この日誌を逆再生してセーブポイントの目印まで正確に巻き戻す。
* **MVCC（多版型同時実行制御: 世代管理）**:
  * 読み書きが互いに衝突しないようにするための仕組み。データを上書きせず新旧バージョンを並べて保持する。
  * 「まだコミットされていないトランザクションの変更は、他の接続には見せない」という制御を行うことで、セーブポイント中の未確定データが外部に漏れないように隠蔽する。

## 5. テストコードへの応用（裏ワザ的アプローチ）

本来は「業務バッチでのエラー救済」のために生まれた SAVEPOINT ですが、**Webアプリケーションのテスト自動化において極めて強力な裏ワザ（業界標準パターン）** として活用されています。

* **課題**: テストごとにデータをきれいに消したいが、毎回テーブルを削除・再作成（DROP/CREATE）したり DELETE 文を投げるのは遅すぎる。
* **解決策**:
  1. テスト開始時に親トランザクションを開く。
  2. アプリのコードが `commit()` を呼んでも、裏で **セーブポイントの処理にすり替えて本コミットを空振りさせる**。
  3. テスト関数が終わった瞬間に、親トランザクションを **`ROLLBACK` して一撃で白紙に戻す**。
この仕組みにより、「アプリには通常通りコミットが成功したと思わせつつ、DB上は一切汚さずに超高速でテストを回す」という理想的なテスト環境が実現できます。

## 6. SQLAlchemy を使ったアプリのテストでの利用（コミット回避トリックの深層）

### (1) 結論：テストで SAVEPOINT を使う真の理由
テストで SAVEPOINT（SQLAlchemy における `begin_nested()`）を使う理由は、**「セーブポイント地点へ巻き戻す（部分ロールバックする）」という本来の機能を使うためではありません**。

本質は、**「SQLAlchemy 内部で `commit()` の挙動が切り替わるスイッチ」を利用し、アプリコードによる本物の COMMIT を回避するための防壁（ダミーコミット発生器）としてあえて SAVEPOINT を使う**という点にあります。

* **本来の目的**: エラー時に `ROLLBACK TO SAVEPOINT` を使って部分的に巻き戻し、リトライやスキップを行うこと。
* **テストでの目的**: `ROLLBACK TO` は一切使わない。アプリコードの `session.commit()` が本物の `COMMIT` を発行してトランザクションが確定・終了してしまうのを防ぐこと。

---

### (2) DB（PostgreSQL）と ORM（SQLAlchemy）の仕様の違い

このトリックを理解する上で極めて重要なのが、**「PostgreSQL 本体の仕様」と「SQLAlchemy の実装（翻訳機能）」のレイヤーの違い**です。

#### ① PostgreSQL（生SQL）の仕様
PostgreSQL には「ネストされたトランザクション」という概念自体は存在しません。また、セーブポイントがあっても `COMMIT` を実行すると**容赦なくトランザクション全体が実コミットされて終了**します。
```sql
BEGIN;
SAVEPOINT sp1;
INSERT INTO users VALUES (1, 'Alice');
COMMIT;  -- ← PostgreSQL は SAVEPOINT を無視して全体を本確定・終了する
         --   （SAVEPOINT があっても COMMIT を自動ですり替えたりはしない）
```

#### ② SQLAlchemy の Session 実装（翻訳スイッチ）
SQLAlchemy の `Session` は、自身が「セーブポイント内（`begin_nested()` の下）にあるかどうか」を内部状態として記憶しています。

| 状態 | `session.commit()` を呼んだときの挙動 | 発行される SQL |
| :--- | :--- | :--- |
| 通常時（外側Tx） | トランザクションを本確定する | **`COMMIT`**（本物） |
| **`begin_nested()` 下** | **直前のセーブポイントを解放するだけ** | **`RELEASE SAVEPOINT`**（ダミー） |

テストパターンでは、まさにこの **「`begin_nested()` 状態にしておけば、アプリが `commit()` を呼んでも `RELEASE SAVEPOINT` にすり替えてくれる」という SQLAlchemy 独自の翻訳機能** を逆手に取っています。

### (3) テストにおけるトランザクションライフサイクルの全貌

pytest などのフィクスチャ（`scope="function"`）を使い、テスト関数ごとに以下のライフサイクルを回します。

```text
【テスト関数 1回分の実行フロー】

テスト開始 (fixture setup)
  │
  ├─ connection.begin()           ← ① 本物のトランザクション開始 (BEGIN)
  ├─ session.begin_nested()       ← ② 最初の防壁を作成 (SAVEPOINT sa1)
  │
  │  ─── ここから FastAPI / アプリコードの処理 ───
  │
  ├─ session.add(user) / flush()  ← 変更が積み重なる (同Tx内なので後続のSELECTからも参照可能)
  ├─ session.commit()             ← ③ アプリはコミットしたつもりだが、
  │                                   防壁のおかげで「RELEASE SAVEPOINT sa1」にすり替わる！
  │                                   （本コミットされないため、外側のTxは維持される）
  │
  ├─ (自動で session.begin_nested()) ← ④ 防壁が消費されたので、即座に次の防壁 (SAVEPOINT sa2) を再作成
  │                                   （次の commit() が本物になる事故を防ぐ）
  │
  │  ─── テスト終了 (fixture teardown) ───
  │
  └─ transaction.rollback()       ← ⑤ 最後に外側から本物の ROLLBACK を一撃！
                                     sa1, sa2, 全ての変更が綺麗サッパリ消滅する
```

#### ポイント A: なぜ `after_transaction_end` リスナーで再 `begin_nested()` するのか？
アプリの `commit()` によって `RELEASE SAVEPOINT sa1` が走ると、防壁（セーブポイント）が消失します。もしアプリが1つの処理の中で2回以上 `commit()` を呼ぶ設計だった場合、2回目の `commit()` は「通常時」と判定されて**本物の COMMIT が DB に届いてしまいます**。
そのため、セーブポイントが閉じられた直後にイベントリスナーで即座に新しい `begin_nested()` を張り直す必要があります。

#### ポイント B: 同一テスト内での変更の可視性
「コミットを RELEASE にすり替えたら、直後にアプリが SELECT してもデータが取れないのでは？」という心配は不要です。同一トランザクション（同じ TxID）の中での変更は、MVCC 的にも自分自身のトランザクションからは常に最新の変更が見えるため、アプリは通常通り「コミットして確定した状態」として読み書きを続行できます。

#### ポイント C: テスト間の完全な独立性
テスト関数が終わるたびに親トランザクションを `ROLLBACK` し、次のテスト関数では新しい `connection.begin()` からやり直すため、前テストのゴミデータが残ることは絶対にありません。

### (4) 総括

```text
┌────────────────────────────────────────────────────────────────────────┐
│  本来の用途:                                                           │
│  何か問題が起きたときに `ROLLBACK TO` で特定の目印まで戻るための機能   │
│                                                                        │
│  テストでの用途（ハック）:                                             │
│  `ROLLBACK TO` は使わない。アプリの `commit()` を `RELEASE` に化けさせ、│
│  外側の親トランザクションを安全に維持し続けるための「防護壁」として使う │
└────────────────────────────────────────────────────────────────────────┘
```

セーブポイント本来の目的（小分けにして巻き戻す）ではなく、**SQLAlchemy の `commit()` を無力化・無害化するための手段として SAVEPOINT 機構をあえて利用している**というのが、このテストパターンの正体です。
