# SQL SAVEPOINT の基礎とトランザクションライフサイクル - 学習ノート

## 1. SAVEPOINT とは？

**SAVEPOINT（セーブポイント）** は、すでに開始されているトランザクションの内部に打つことができる**「しおり（チェックポイント・目印）」**です。

### 名前の由来
ゲームのセーブポイントと全く同じ概念です。
* **ゲーム**: ボス戦の直前にセーブポイントを作っておけば、負けてゲームオーバーになっても最初からやり直す必要はなく、**直前のセーブポイントまで巻き戻してリトライ**できる。
* **データベース**: 長いトランザクションの途中に `SAVEPOINT 目印名` を打っておけば、途中でエラーが起きても全体を破棄せず、**その目印の地点まで部分的に巻き戻す（部分ロールバック）**ことができる。

---

## 2. SQL に導入されたそもそもの背景と経緯

標準SQL（SQL99）で規格化された機能ですが、導入の背景には従来のトランザクション仕様が抱えていた「硬さ」がありました。

### 従来のトランザクションの限界（All or Nothing の壁）
データベースのトランザクションは本来「**ACID特性**」に基づき、**「すべて成功（COMMIT）か、すべて失敗（ROLLBACK）か」** の二者択一（All or Nothing）です。

しかし、実際の業務システムではこの厳密さが不便になるケースがありました：
* **大規模バッチ処理の例**:
  * 10,000件のデータを1件ずつループ処理して登録している最中、**9,999件目で1件だけ不正データがありエラーになった**とする。
  * SAVEPOINT がない場合：トランザクション全体がロールバックされるため、**正常に処理が終わっていた最初の9,998件も道連れで消滅**し、何時間もの処理が最初からやり直しになる。

このような「一部の失敗のために、それまでの正常な処理まで全て捨てるのはコストが高すぎる」という現場の切実な課題を解決するために、**トランザクションを壊さずに途中まで巻き戻せる「部分ロールバック（Partial Rollback）」** として SAVEPOINT が導入されました。

> [!NOTE] 実務上の注意：PostgreSQL のサブトランザクション問題
> 概念としては上記のように理解できますが、実務の大規模バッチ（数万件規模）で 1 件ごとに SAVEPOINT を打つのは避けるのが定石です。PostgreSQL では SAVEPOINT を大量（64個以上）に生成すると、共有メモリのキャッシュ溢れ（Subtransaction Cache Overflow）が発生し、DB 全体のパフォーマンスが劇的に低下します。そのため、実務の大規模バッチでは「1,000 件ごとに本コミットしてトランザクションを分割する（チャンク処理）」のが基本です。

## 3. 本来想定されていたユースケース

SQLの仕様として想定されていた主な用途は以下の通りです。

1. **エラーリカバリとリトライ**
   * 処理の直前にセーブポイントを打ち、エラーが発生したらセーブポイントまで巻き戻して別のアプローチを試す。
2. **一部スキップによるバッチ継続**
   * エラーが起きた1件だけをセーブポイントまで巻き戻して破棄・エラーログ出力し、残りの正常なレコードの処理をそのまま続行して最後に一括コミットする。
3. **複雑なビジネスロジックの分岐**
   * ネストしたサブルーチンや関数ごとに安全圏を確保しながら処理を進める。

## 4. 技術的な仕組み（要点）

### (1) コミットとセーブポイントの違い、および PostgreSQL の可視性・SubXID の仕組み

#### コミットとセーブポイントの基本的な違い
* **コミット (`COMMIT`)**: トランザクション全体の変更を確定・ディスクへ永続化し、他トランザクションへ公開してトランザクションを終了します。
* **セーブポイント (`SAVEPOINT`)**: データを確定させるものではなく、エラー発生時などに「同一トランザクション内の特定地点まで部分的に巻き戻す（部分ロールバックする）」ための目印（チェックポイント）です。

#### 直前の変更が見える理由（PostgreSQL の MVCC と XID）
前提として、**PostgreSQL の MVCC（多版型同時実行制御）によるトランザクション内可視性の仕組み**により、一つのトランザクション内では、「直前に `INSERT` や `UPDATE` したデータを、直後の `SELECT` や `UPDATE` で参照・更新できる」という仕組みになっている。
* PostgreSQL では、各行（タプル）のヘッダに変更元のトランザクション ID（XID: `xmin` / `xmax`）や、トランザクション内の何番目のコマンドかを示すコマンド ID（`cmin` / `cmax`）が記録されます。
* 問い合わせ時にはこれらを参照し、「自分自身の XID かつ、現在のコマンドより前に実行された変更」であれば即座に可視と判定されます。そのため、セーブポイントの有無に関わらず、トランザクション内で行った作業中データは自分自身からは常に参照できます。

#### セーブポイントの本質：SubXID（サブトランザクション）と「栞（しおり）」
PostgreSQL 内部において、セーブポイントは **サブトランザクション（Subtransaction）** として実装されています。
セーブポイントを打つと内部で **SubXID（サブトランザクション ID）** が発行され、以降の変更はその SubXID に紐づいて記録されます。これは、本を読み進める際に挟む **「栞（しおり）」** のような役割を果たします。

* **`ROLLBACK TO SAVEPOINT`（栞の位置へ戻る）**:
  エラーが起きた際、「栞を挟んだ位置まで戻り、それ以降（その SubXID）で行った変更だけを無効化」します。親トランザクション全体をアボートさせずに、安全に部分的なリトライが可能です。
* **`RELEASE SAVEPOINT`（栞を抜く）**:
  「もうこの地点へ戻る必要がなくなったため、目印（栞）を片付けた」状態です。データが確定（コミット）されたわけではなく、ロールバック用のチェックポイントを破棄しただけに過ぎません。

#### 確定権限を持つのは「親トランザクションの COMMIT」のみ
栞（セーブポイント）をどれだけ打とうと、あるいは抜こうと、親トランザクションが継続している限りはすべて未コミットの作業中データです。
最終的に親トランザクションが `COMMIT` されて初めて全変更（各 SubXID の変更含む）がディスクへ永続化され、親トランザクションが `ROLLBACK` されればすべて白紙に戻ります。

### (2) DB内部の仕組み（CLOG / MVCC と高速ロールバック）
セーブポイントへのロールバックが高速かつ安全に動く背景には、データベースのトランザクション管理機構（特に PostgreSQL）が深く関わっています。

* **PostgreSQL の実態（CLOG と MVCC の連携）**:
  1. セーブポイント以降に行われた INSERT や UPDATE は、それぞれ固有の**サブトランザクションID（Subxid）**を持ってテーブル（ヒープ領域）に書き込まれます。
  2. `ROLLBACK TO SAVEPOINT` が実行されると、PostgreSQL はコミットログ（**CLOG** / `pg_xact`）上でそのサブトランザクションIDを **「アボート（中絶・無効）」とマークするだけ** です。
  3. テーブル上の行データ自体は物理的にはその場に残りますが、**MVCC（多版型同時実行制御）** の可視性判定によって「アボートされたIDのデータは誰からも見えない」と扱われます。
  * このため、変更したデータ量に関わらず **一瞬でロールバックが完了** します（不要になったデッドタプルは後から VACUUM が掃除します）。
* **（参考）MySQL (InnoDB) の場合**:
  * InnoDB では、ロールバックには WAL（Redo ログ）ではなく **Undo（アンドゥ）ログ** を使用して変更前の値に戻します。Redo ログ（WAL）は電源断などの障害復旧時にコミット済みデータを復元（前進再生）するためのものです。

## 5. テストコードへの応用（セーブポイントと高速ロールバックテスト）

本来は「業務バッチでのエラー救済」のために生まれた SAVEPOINT ですが、**Webアプリケーションのテスト自動化において極めて強力なクリーンアップ手法（業界標準パターン）** として活用されています。

* **課題**: テストごとにデータをきれいに消したいが、毎回テーブルを削除・再作成（DROP/CREATE）したり DELETE 文を投げるのは遅すぎる。
* **解決策の仕組み**:
  1. **親トランザクションの開始**: テスト開始時に、テスト全体を包む外側の親トランザクションを開始する（`connection.begin()`）。
  2. **最初の DB 操作時に自動で SAVEPOINT を作成**: SQLAlchemy のセッション（`join_transaction_mode="create_savepoint"`）は、最初の DB 操作（SELECT/INSERT 等）が行われた瞬間に、自動で `SAVEPOINT` を発行して防壁を張る。
  3. **`Session.commit()` の二重実装によるコミット回避**:
     * この SQLAlchemy の Session に実装されているメソッドは内部状態に応じた**二重実装**（通常時は本物の `COMMIT` を発行、セーブポイント管理下では `RELEASE SAVEPOINT` を発行）になっている。
     * そのため、 `RELEASE SAVEPOINT` が発行されて DB 側の本コミットが回避される（アプリ側には正常にコミットが完了したように見せかける）。
  4. **解放後に即座に次のセーブポイントを再作成**:
     * `RELEASE SAVEPOINT` によって直前のセーブポイントが消費された後、続く次の DB 操作時に SQLAlchemy が**即座に新しい `SAVEPOINT` を自動で再作成**する。
     * これにより、アプリ内で複数回 `commit()` が呼ばれても、本物の `COMMIT` が DB に到達する隙を作らない。
  5. **テスト終了時の一撃ロールバック**:
     * テスト関数が終わった瞬間に、最初に開いた親トランザクションを **`ROLLBACK`** する。
     * テスト中にどれだけセーブポイントの作成と解放が繰り返されていようと、親トランザクションのロールバックによって**すべての変更が一瞬で跡形もなく白紙に戻る**。

この仕組みにより、「アプリコードには通常通りコミットが成功したと思わせつつ、DB 上は一切汚さずに超高速でテストを回す」という理想的なテスト環境が実現できます。

## 6. SQLAlchemy を使ったアプリのテストでの利用（コミット回避トリックの深層）

### (1) 結論：テストで SAVEPOINT を使う真の理由
テストで SAVEPOINT を使う理由は、**「セーブポイント地点へ巻き戻す（部分ロールバックする）」という本来の機能を使うためではありません**。

本質は、**アプリコードが呼ぶ `session.commit()` を本物の `COMMIT` にせず、外側の親トランザクションを維持するための防壁（ダミーコミット発生器）としてセーブポイントを利用する** という点にあります。

* **本来の目的**: エラー時に `ROLLBACK TO SAVEPOINT` を使って部分的に巻き戻し、リトライやスキップを行うこと。
* **テストでの目的**: `ROLLBACK TO` は一切使わない。アプリコードの `session.commit()` が本物の `COMMIT` を発行してトランザクションが確定・終了してしまうのを防ぐこと。

---

### (2) DB（PostgreSQL）と ORM（SQLAlchemy）の仕様の違い

このトリックを理解する上で極めて重要なのが、**「PostgreSQL 本体の仕様」と「SQLAlchemy の実装（翻訳機能）」のレイヤーの違い**です。

#### ① PostgreSQL（生SQL）の仕様
PostgreSQL には「ネストされたトランザクション」という概念自体は存在しません。また、セーブポイントがあっても生SQLで `COMMIT` を実行すると**容赦なくトランザクション全体が実コミットされて終了**します。
```sql
BEGIN;
SAVEPOINT sp1;
INSERT INTO users VALUES (1, 'Alice');
COMMIT;  -- ← PostgreSQL は SAVEPOINT を無視して全体を本確定・終了する
         --   （SAVEPOINT があっても COMMIT を自動ですり替えたりはしない）
```

#### ② SQLAlchemy の Session 実装（二重実装による動作分岐）
SQLAlchemy の `Session.commit()` は、自身がセーブポイント管理下にあるかどうかを内部状態として追跡しており、それに応じた**二重実装**（状態による多態的な動作分岐）になっています。

| 状態 | `session.commit()` を呼んだときの挙動 | 発行される SQL |
| :--- | :--- | :--- |
| 通常時（外側Tx） | トランザクションを本確定する | **`COMMIT`**（本物） |
| **セーブポイント管理下** | **直前のセーブポイントを解放する** | **`RELEASE SAVEPOINT`**（コミットの代用） |

テストパターンでは、まさにこの **「セーブポイント管理下にしておけば、アプリが呼ぶ `session.commit()` が SQLAlchemy の内部実装によって `RELEASE SAVEPOINT` を発行してくれる」という仕様** を利用しています。

### (3) SQLAlchemy v1 から v2 への進化：泥臭いハックから公式機能へ

この「セーブポイントでコミットを回避する」テストパターンは以前から知られていましたが、**SQLAlchemy v1 系から v2 系（1.4以降）にかけて実装方式が劇的に進化**しました。

#### 【v1時代】泥臭いイベントリスナー方式（古い書き方）
かつて SQLAlchemy 1.3 以前では、セッション作成時に自動でセーブポイントを維持する仕組みがありませんでした。そのため、以下のように `@event.listens_for` を使って手動でセーブポイントを張り直す必要がありました。

```python
# ⚠️ SQLAlchemy 1.x 時代の古い書き方（参考）
connection = engine.connect()
transaction = connection.begin()
session = Session(bind=connection)

# 1. 最初のセーブポイントを手動で開始
nested = connection.begin_nested()

# 2. commit() されるとセーブポイントが破棄されるため、イベントリスナーで即座に再作成
@event.listens_for(session, "after_transaction_end")
def restart_savepoint(session, transaction):
    # 外側のトランザクションが終了したのではなく、ネストされたTxが終わった場合のみ再開
    if transaction.nested and not transaction._parent.nested:
        session.begin_nested()
```
* **v1 の課題**:
  * イベントリスナーの条件分岐が複雑で、SQLAlchemy の非公開プライベート変数（`_parent`）に依存している。
  * 初見の開発者には何をしているのか理解不能で、ライブラリのアップデートで壊れやすい「黒魔術」だった。

#### 【v2時代（1.4以降）】`join_transaction_mode="create_savepoint"` による公式標準化（現在の書き方）
SQLAlchemy 1.4 / 2.0 では、この長年のテスト需要に応えるため、公式パラメータとして **`join_transaction_mode="create_savepoint"`** が導入されました。

現在 `backend/tests/conftest.py` で採用されているのが、まさにこのモダンな方式です：

```python
# ✅ SQLAlchemy 2.0 のモダンな書き方（backend/tests/conftest.py）
connection = engine.connect()
transaction = connection.begin()

session = Session(
    bind=connection,
    join_transaction_mode="create_savepoint",  # ← この1行で自動化完了！
)
```

* **v2 で何が変わったのか？**:
  イベントリスナーを手動で書く必要は完全に撤廃されました。SQLAlchemy の `Session` 自身が「外側で既にトランザクションが開いていること」を検知し、**以下のサイクルを完全自動で代行** してくれます：
  1. 最初の DB 操作時に、自動で **`SAVEPOINT`** を発行する。
  2. アプリが `session.commit()` を呼んだら、自動で **`RELEASE SAVEPOINT`** を発行する。
  3. 次にアプリが DB 操作を行ったら、自動で **新しい `SAVEPOINT`** を再発行する。

### (4) テストにおけるトランザクションライフサイクルの全貌

pytest の `db_session` フィクスチャ（`scope="function"`）により、テスト関数ごとに以下のライフサイクルが回ります。

```text
【テスト関数 1回分の実行フロー】

テスト開始 (fixture setup: backend/tests/conftest.py)
  │
  ├─ connection.begin()                ← ① 本物の親トランザクション開始 (BEGIN)
  │                                       ※ session = Session(..., join_transaction_mode="create_savepoint")
  │
  │  ─── ここから FastAPI / アプリコードの処理 ───
  │
  ├─ session.add(user) / execute(...)  ← ② 初回操作時に SQLAlchemy が自動で SAVEPOINT sa_1 を発行
  │
  ├─ session.commit()                  ← ③ アプリはコミットしたつもりだが、
  │                                       Session.commit() の二重実装により「RELEASE SAVEPOINT sa_1」が発行される！
  │                                       （本物の COMMIT ではないため、外側の親 Tx は開いたまま維持）
  │
  ├─ 次の DB 操作                       ← ④ セーブポイント解放を受け、SQLAlchemy が自動で次の防壁「SAVEPOINT sa_2」を即座に再発行
  │
  │  ─── テスト終了 (fixture teardown: backend/tests/conftest.py) ───
  │
  ├─ session.close()                   ← ⑤ セッションのメモリ解放
  └─ transaction.rollback()            ← ⑥ 外側の親トランザクションを本物の ROLLBACK で一撃！
                                          sa_1, sa_2 を含むテスト内の全変更が綺麗サッパリ消滅する
```

#### ポイント A: なぜテスト間でデータが汚染されないのか？
テスト関数が終わるたびにフィクスチャの teardown で親トランザクション（`connection.begin()`）を `ROLLBACK` します。アプリが途中で何度 `commit()` を呼んでいたとしても、すべてセーブポイントの解放（`RELEASE SAVEPOINT`）として処理されているため、親トランザクションの `ROLLBACK` 一発ですべての変更が跡形もなく消滅します。

#### ポイント B: 同一テスト内での変更の可視性
「コミットではなく RELEASE SAVEPOINT が発行されたら、直後にアプリが SELECT してもデータが取れないのでは？」という心配は不要です。同一トランザクション（同じ接続）の中での変更は、MVCC 的にも自分自身からは常に最新の変更が見えるため、アプリ側は「通常通りコミットが完了した状態」として読み書きを続行できます。

### (5) 総括

```text
┌────────────────────────────────────────────────────────────────────────┐
│  本来の用途:                                                           │
│  何か問題が起きたときに `ROLLBACK TO` で特定の目印まで戻るための機能   │
│                                                                        │
│  テストでの用途（ハック）:                                             │
│  `ROLLBACK TO` は使わない。アプリの `commit()` を `RELEASE` に化けさせ、│
│  外側の親トランザクションを安全に維持し続けるための「防護壁」として使う │
└────────────────────────────────────────────────────────────────────────┘
```

セーブポイント本来の目的（小分けにして巻き戻す）ではなく、**SQLAlchemy の `commit()` を無害化するための手段として SAVEPOINT 機構をあえて利用している**というのが、このテストパターンの正体です。
そして SQLAlchemy 2.0 では `join_transaction_mode="create_savepoint"` により、この裏ワザが「洗練された公式標準機能」として誰でも安全・直感的に使えるようになっています。
