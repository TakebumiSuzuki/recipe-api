# 課題プロジェクト：レシピ共有 API

## 1. このドキュメントは何か

FastAPI の学習で身につけた内容を、**手本を見ずに自分で設計して書く**ための課題定義。

これまでのプロジェクトは、章ごとに説明を受けながら進めてきた。
ここでは逆に、**先に完成形の仕様だけを決めておき、実装は自分で考える**。
詰まったときに読み返す地図として、このドキュメントを使う。

対象読者は、FastAPI で以下を一通り書いたことがある人。

- パス／クエリパラメータ、Pydantic のリクエストボディと `response_model`
- `APIRouter` によるファイル分割、`Depends`、pydantic-settings による設定管理
- SQLAlchemy 2.0 のモデル定義、セッション管理、CRUD 層の分離
- Alembic でのマイグレーション、1対多のリレーション
- pytest と `TestClient`、テスト用 DB の分離、TDD

---

## 2. 何を作るのか

**レシピ共有サービスのバックエンド API。**

利用イメージはクックパッドのような料理レシピサイト。ただし今回は画面（フロントエンド）を作らないので、
「ブラウザで見える形」にはならない。Swagger UI（`/docs`）から API を叩いて動作を確認する。

アプリが扱いたいことは次の4つ。

1. 投稿者がレシピを登録する。レシピには**材料（分量つき）**と**手順**が付く。
2. レシピに**タグ**（`時短`、`和食` など）を付け外しする。
3. レシピに**栄養情報**（カロリー・たんぱく質など）を1件だけ紐づける。
4. タグや難易度でレシピを検索し、一覧を返す。

この4つを実現しようとすると、テーブル同士の関係が自然に3種類とも登場する。そこが今回の狙い。

---

## 3. 扱う範囲・扱わない範囲

### 扱う（＝今回の課題に含める）

- **テーブル間の関係を3種類すべて**：1対1、1対多、多対多（2パターン）
- **カラム型のバリエーション**：Enum、Numeric、タイムゾーン付き日時、Text、SmallInteger、JSONB
- **PostgreSQL**（SQLite は使わない）を **Docker Compose** で起動する
- **Alembic** でのマイグレーション。しかも「既存データがある状態でのスキーマ変更」を1回経験する
- **ロギング設定**（アプリのログと uvicorn のログの形式を揃える、リクエストIDを付ける）
- **TDD**：エンドポイントはすべてテストを先に書いてから実装する

### 扱わない（＝あえて外す）

- **ログイン・認証・セッション管理**（未学習のため）。
  `users` テーブルは作るが、これは「レシピの投稿者は誰か」を表すだけのもので、
  パスワードもトークンも扱わない。「誰でも誰の名前でも投稿できる」状態で構わない。
- **`async` / `await`（非同期）**（未学習のため）。すべて同期（`def`）で書く。
- **フロントエンド**。Vue もテンプレートも作らない。
- **SQLModel のような ORM とスキーマを統合するライブラリ**。
  SQLAlchemy のモデルと Pydantic のスキーマは、これまで通り別々に定義する。

## 4. 全体像

### 4-1. データの形

```
  users （投稿者）
    │
    │ 1対多：1人の投稿者が複数のレシピを持つ
    ↓
  recipes （レシピ）─── 1対1 ───→ nutrition_facts （栄養情報）
    │
    ├── 1対多 ──→ steps （手順。1,2,3… と順序を持つ）
    │
    ├── 多対多 ──→ ingredients （材料マスタ）
    │     中間テーブル recipe_ingredients が
    │     「分量」「単位」という追加情報を持つ
    │
    └── 多対多 ──→ tags （タグ）
          中間テーブル recipe_tags は
          紐付けの情報しか持たない
```

多対多を2パターン用意しているのが、このデータ設計の要点。

- **`recipes` ⇄ `tags`**：「このレシピにこのタグが付いている」以上の情報がない。
  中間テーブルは2つの外部キーだけを持つ。SQLAlchemy では `secondary` という引数に
  テーブルを渡す書き方になり、中間テーブル用のモデルクラスは作らない。
- **`recipes` ⇄ `ingredients`**：「このレシピにこの材料が使われている」に加えて、
  **「200 グラム」という分量**が必要になる。この分量は、レシピにも材料にも属さない
  （＝`recipes` にも `ingredients` にも置き場所がない）。
  そのため中間テーブル自体を1つのモデルクラスとして定義する。
  この書き方を **association object**（関連オブジェクト）と呼ぶ。

> **注**：多対多で「中間テーブルに追加カラムを持たせたくなったら association object」
> という判断は、実務でも頻繁に出てくる分岐点。今回はその両方を1つのアプリの中で書き比べる。

### 4-2. コードの置き場所

これまでのプロジェクトと同じ**レイヤー別**の構成にする。

```
recipe-api/
├── compose.yml               # PostgreSQL を起動する
├── .env / .env.example       # 接続情報。.env は git に入れない
├── backend/
│   ├── app/
│   │   ├── core/
│   │   │   ├── config.py     # Settings（環境変数の読み込み）
│   │   │   ├── session.py    # engine と sessionmaker
│   │   │   ├── logging.py    # ロガー設定
│   │   │   └── error_handlers.py
│   │   ├── models/           # SQLAlchemy のテーブル定義
│   │   ├── schemas/          # Pydantic の入出力の形
│   │   ├── crud/             # DB の読み書き
│   │   ├── routes/           # エンドポイント
│   │   └── deps.py           # Depends で配る共通部品
│   ├── alembic/
│   ├── tests/
│   └── main.py
└── docs/
```

前回との違いは `schemas` と `models` がどちらもフォルダになること。
モデルが8つに増えるため、1ファイルでは読みづらくなる。

### 4-3. 1リクエストが通る道

```
クライアント（Swagger UI / pytest の TestClient）
   ↓  JSON
routes/    ── リクエストを受け取り、Pydantic で検証する。DB 操作は書かない
   ↓  Python のオブジェクト
crud/      ── SQLAlchemy でテーブルを読み書きする。HTTP のことは知らない
   ↓  SQL
PostgreSQL（Docker コンテナの中）
```

「routes は薄く、crud は DB だけ」という線引きは前回と同じ。

## 5. テーブル定義

型は「こういう性質のデータを入れたい」という意図で書いている。
SQLAlchemy でどう書くか（`mapped_column` の引数など）はモデル側で定義する。
なお、制約やインデックスの命名規則は `app/models/base.py` の `naming_convention`（`ix`, `uq`, `ck`, `fk`, `pk`）に従って自動命名させる。

### users（投稿者）

| 意図 | 内容 |
| --- | --- |
| `id` | 主キー |
| `name` | 表示名。文字列、最大50文字 |
| `email` | 文字列、最大255文字。**重複禁止** |
| `bio` | 自己紹介。長文可（Text）、未入力可 |
| `created_at` | 作成日時。**タイムゾーン付き**、DB 側で自動的に現在時刻が入る |
| `updated_at` | 更新日時。**タイムゾーン付き**、DB 側で自動的に現在時刻が入り、更新時にも自動更新される |

制約として次の内容を入れる。

- `name` は空白を除いて 2 文字以上（CheckConstraint: `length(trim(name)) >= 2`）
- `bio` は 1000 文字以下（CheckConstraint: `length(bio) <= 1000`）
- `bio` は空白のみ不可（CheckConstraint: `bio IS NULL OR length(trim(bio)) >= 1`）
- `email` は簡易正規表現によるメール形式チェック（CheckConstraint: `email ~ '^[^@]+@[^@]+\.[^@]+$'`）
- `email` は小文字であること（CheckConstraint: `email = lower(email)`、制約名: `email_lowercase`）
- `email` は重複禁止（一意制約）

> レシピとのリレーションには `passive_deletes=True` を設定する（投稿者が削除された場合、レシピ側の `user_id` は DB の `ON DELETE SET NULL` により `NULL` に更新され、レシピ自体は保持される）。

> **タイムゾーン付き日時**：PostgreSQL の `timestamptz` 型のこと。
> 「2026-08-24 10:00」だけでなく「どこの時刻か」まで保存する。
> 日本国内向けサービスでも、サーバとDBのタイムゾーンがずれると事故になるため、付きを使うのが定石。

### recipes（レシピ）

| 意図 | 内容 |
| --- | --- |
| `id` | 主キー |
| `user_id` | `users.id` への外部キー（1対多の「多」側）。**未入力可**、ユーザー削除時は `SET NULL` |
| `title` | 文字列、最大100文字 |
| `description` | 説明文。長文可（Text）、未入力可 |
| `servings` | 何人分か。整数 |
| `cook_time_min` | 調理時間（分）。整数 |
| `difficulty` | `easy` / `normal` / `hard` のいずれか（非ネイティブ Enum: VARCHAR + CHECK制約 `difficulty_values`） |
| `source` | 出典情報。JSONB、未入力可 |
| `published_at` | 公開日時。**タイムゾーン付き日時**、未公開なら空（NULL） |
| `created_at` / `updated_at` | タイムゾーン付き日時。作成時・更新時に自動設定 |

制約・インデックスとして次の内容を入れる。

- 同じ投稿者が同じタイトルのレシピを2つ作れないようにする（`user_id` と `title` の複合ユニーク制約）
- `title` は空白を除いて 1 文字以上（CheckConstraint: `length(trim(title)) >= 1`）
- `servings` は 1 以上（CheckConstraint: `servings >= 1`）
- `description` は 5000 文字以下（CheckConstraint: `length(description) <= 5000`）
- `description` は空白のみ不可（CheckConstraint: `description IS NULL OR length(trim(description)) >= 1`）
- `cook_time_min` は 1 以上（CheckConstraint: `cook_time_min >= 1`）
- `source` に GIN インデックスを設定
- `user_id` は外部キー削除時に `SET NULL`（`ondelete="SET NULL"`）

> **`published_at` をタイムゾーン付き日時にした理由**：
> 「公開日（`published_on: Date`）」をサーバー側の UTC で保存すると、時差によってユーザーの現地時間の日付とずれる問題（例: JST 9/5 朝 8:00 に公開すると UTC では 9/4 23:00 となり前日公開になってしまう）が発生する。
> そのため、日付単体ではなく正確な瞬間を記録するタイムゾーン付き日時の `published_at` を採用している。また、未公開時は `NULL` とすることで、真偽値カラム `is_published` を持たずに「`published_at` が存在するか否か」で公開・非公開を判定できる。

> **`source` を JSONB にした理由**：出典はレシピによって形が違う。
> 「URL だけ」のこともあれば「書籍名＋著者＋ページ番号」「番組名＋放送日」のこともある。
> こういう「項目が事前に決まらないデータ」を1カラムにそのまま入れられるのが JSONB。
> ただし何でも JSONB に入れると検索も制約もできなくなるため、使いどころの見極めが必要になる。
> （この設計が妥当かどうかは、実装時に改めて議論する）

### steps（手順）

| 意図 | 内容 |
| --- | --- |
| `id` | 主キー |
| `recipe_id` | `recipes.id` への外部キー |
| `step_no` | 何番目の手順か。小さい整数 |
| `instruction` | 手順の本文。長文可 |

制約：同じレシピの中で `step_no` は重複しない（`recipe_id` と `step_no` の複合ユニーク制約）。

> リレーショナルDBのテーブルには**行の順序という概念がない**。
> 「1. 玉ねぎを切る → 2. 炒める」の順序を保つには、`step_no` のような列を自分で持ち、
> 取り出すときに明示的に並び替える必要がある。

### ingredients（材料マスタ）

| 意図 | 内容 |
| --- | --- |
| `id` | 主キー |
| `name` | 材料名。文字列、最大50文字、**重複禁止** |

「玉ねぎ」という材料を1行だけ持ち、複数のレシピから参照する。

### recipe_ingredients（レシピと材料をつなぐ／追加カラムあり）

| 意図 | 内容 |
| --- | --- |
| `recipe_id` | `recipes.id` への外部キー |
| `ingredient_id` | `ingredients.id` への外部キー |
| `quantity` | 分量。小数を扱う Numeric |
| `unit` | `g` / `ml` / `個` / `大さじ` / `小さじ` のいずれか（Enum） |
| `note` | 「みじん切り」などの補足。文字列、未入力可 |

`recipe_id` と `ingredient_id` の2つで主キーにする（複合主キー）。
これにより「同じレシピに同じ材料が2行登録される」ことを DB が防いでくれる。

> **分量に浮動小数点（float）を使わない理由**：`0.1` のような値が誤差を持つため。
> 金額や分量のように「表示した通りの値であってほしい」ものには Numeric（10進数）を使う。

### tags（タグ）

| 意図 | 内容 |
| --- | --- |
| `id` | 主キー |
| `name` | タグ名。文字列、最大30文字、**重複禁止** |

### recipe_tags（レシピとタグをつなぐ／追加カラムなし）

`recipe_id` と `tag_id` の2つの外部キーのみ。この2つで複合主キー。
モデルクラスは作らず、SQLAlchemy の `Table` として定義する。

### nutrition_facts（栄養情報）

| 意図 | 内容 |
| --- | --- |
| `recipe_id` | `recipes.id` への外部キー。**かつ、これ自体が主キー** |
| `calories` | カロリー。Numeric |
| `protein_g` / `fat_g` / `carb_g` | たんぱく質・脂質・炭水化物（グラム）。Numeric |

**1対1をどう作るか**がここの学びどころ。
外部キーを主キーにすると、`recipe_id` は重複できない（主キーだから）。
その結果「1つのレシピに栄養情報は最大1行」が DB のレベルで保証される。
SQLAlchemy 側では `relationship()` に「1件しか返さない」設定を加える。

## 6. API 一覧

すべて `/api/v1` の下に置く。TDD で作る順番は「進め方」の章を参照。

**投稿者**

- `POST /users` … 投稿者を登録する
- `GET /users/{user_id}` … 1人取得する
- `GET /users/{user_id}/recipes` … その人のレシピ一覧

**レシピ**

- `POST /recipes` … レシピを登録する。材料・手順・タグを**入れ子のJSONで一括受け取り**する
- `GET /recipes/{recipe_id}` … 材料・手順・タグ・栄養情報まで入れ子で返す
- `GET /recipes` … 一覧。ページネーションと絞り込み（`tag` / `difficulty` / `user_id` / `is_published`（`published_at` の有無で判定））
- `PATCH /recipes/{recipe_id}` … 部分更新（送られてこなかった項目は変更しない）
- `DELETE /recipes/{recipe_id}` … 削除。関連する手順・材料の紐付けも消える

**栄養情報（1対1）**

- `PUT /recipes/{recipe_id}/nutrition` … 無ければ作る、有れば置き換える
- `GET /recipes/{recipe_id}/nutrition`

**タグ（追加カラムなしの多対多）**

- `POST /recipes/{recipe_id}/tags` … タグを付ける
- `DELETE /recipes/{recipe_id}/tags/{tag_id}` … タグを外す
- `GET /tags` … タグ一覧（使われている件数つき）

**材料**

- `GET /ingredients?q=たま` … 材料名の部分一致検索
- `POST /ingredients` … 材料マスタに追加する

**その他**

- `GET /health` … アプリと DB の疎通確認

## 7. 進め方

### 進め方の原則

この課題は「動くものを最短で作る」ためのものではなく、**詰まった場所を自分で特定できるようになる**
ためのもの。そのため次の3つを守る。

1. **1ステップで新しくすることは1つに絞る。**
   DB 接続とモデル定義とテストを同時に書くと、エラーが出たときに原因が3つの候補に散る。
2. **各ステップに「終わったと言える確認方法」を決めてから始める。**
   確認方法が思いつかないステップは、まだやることが大きすぎるというサイン。
3. **テーブルは8つ一度に作らない。** 2つから始めて、関係を1種類ずつ足していく。
   マイグレーションを何度も書くことになるが、それは損ではなく Alembic の練習そのもの。

全体は6つの段階に分かれる。

```
第1段階  土台            DB が立ち、アプリから繋がる
第2段階  最初の2テーブル  モデルとマイグレーションの型を作る
第3段階  ログとテスト     以降ずっと使う「観測手段」を先に用意する
第4段階  関係を増やす     1対多 → 多対多(2種) → 1対1 を1つずつ
第5段階  読み取り側       一覧・検索・N+1
第6段階  変更と仕上げ     更新・削除・スキーマ変更
```

---

### 第1段階：土台

#### Step 1. リポジトリと uv プロジェクトを作る

- **ねらい**：手を動かす場所を用意する
- **やること**：新しいディレクトリを作り、`backend/` の中で `uv init`、FastAPI を追加する
- **終わったと言える状態**：`uv run python -c "import fastapi"` がエラーなく終わる
- **前回との違い**：なし。ここは復習

#### Step 2. Docker Compose で PostgreSQL を起動する

- **ねらい**：**Python を1行も書かずに**、DB 単体で動く状態を確認する
- **やること**：`compose.yml` に db サービスを1つ定義する。以下の3つを含める
  - データを保存するボリューム（コンテナを消してもデータが残るようにする）
  - ヘルスチェック（DB が「起動した」ではなく「接続を受け付けられる」状態を判定する仕組み）
  - ユーザー名・パスワード・DB名を環境変数から渡す
- **終わったと言える状態**：`docker compose up -d` の後、`psql` でログインでき、`\dt` が
  「リレーションがありません」と返す（＝繋がっているが、まだテーブルは無い）
- **つまずきやすい点**：devcontainer の中から DB コンテナに繋ぐときのホスト名。
  `localhost` ではなく**サービス名**で解決する必要がある場合がある。ここで一度つまずくと、
  後で「アプリからだけ繋がらない」ときの原因切り分けが早くなる

#### Step 3. 設定・セッション・`/health`

- **ねらい**：**psql(コマンドラインツール) からではなく FastAPI アプリのプロセスから** DB に届くことを確認する。
  経路は `ブラウザ → FastAPI → SQLAlchemy → psycopg → Postgres`。テーブルもモデルもまだ無い
- **やること**：
  - `psycopg` を追加する（SQLAlchemy は SQL を組み立てるだけで、通信はドライバの仕事）
  - `app/core/config.py`：`BaseSettings` で `.env` から接続URLを読む
  - `app/core/db.py`：`create_engine` と `sessionmaker`
  - `app/deps.py`：`yield` する `get_db_session`（`finally` で `close`）
  - `app/main.py`：`GET /health` で `text("SELECT 1")` を投げ、`{"db": "ok"}` を返す
- **終わったと言える状態**：`fastapi dev` を起動し、`/docs` から `/health` を叩くと 200 で
  `{"db": "ok"}`。`docker compose stop db` してから叩くと 500 になる
- **なぜ `SELECT 1` か**：テーブルを参照しないので、テーブルが無い今でも実行できる。
  これが通れば「到達・認証・DB選択」が全部 OK だと分かる
- **なぜこの順か**：モデルを書いてから接続を試すと、接続失敗なのかモデルの書き間違いなのか
  区別がつかない。「繋がることだけ」を先に確定させる

---

### 第2段階：最初の2テーブル

#### Step 4. `users` と `recipes` を書く（1対多）

- **ねらい**：既に一度やった 1対多 を、PostgreSQL で書き直す
- **やること**：`Base` と2つのモデルを定義する。`relationship()` の両側を張る
- **終わったと言える状態**：ファイルを import してもエラーが出ない（まだ DB には反映されない）
- **注意**：この時点ではテーブルは存在しない。作るのは次のステップ

#### Step 5. Alembic を導入して最初のマイグレーション

- **ねらい**：「モデルを書く」と「テーブルができる」が別作業だと体で理解する
- **やること**：`alembic init` → `env.py` にモデルと接続先を教える →
  `alembic revision --autogenerate` → **生成されたファイルを読む** → `alembic upgrade head`
- **終わったと言える状態**：`psql` の `\d recipes` で、外部キーを含む定義が表示される
- **つまずきやすい点**：`env.py` がモデルを import できていないと、
  autogenerate が「差分なし」の空ファイルを作る。**生成物を必ず開いて中身を確認する**

### 第3段階：ログとテスト（＝観測手段）

> ここでいきなり機能を増やさず、先に「見る道具」を用意する。
> この後の段階では、エラーの原因が「SQL の組み立て方」に移っていく。
> ログとテストが無い状態でそこへ進むと、`print` を挿しては消す時間が増える。

#### Step 6. ロギングを設定する

- **ねらい**：以下 3 種類のログを、同じフォーマット（日時・ロガー名・レベル・メッセージ）で統一して stdout（コンソール）に流す
  1. **アプリ独自のログ** (`app.*`): 各エンドポイントやビジネスロジックで書いたログ
  2. **SQLAlchemy の SQL ログ** (`sqlalchemy.engine`): 実際に DB へ発行された SQL（例: `SELECT 1`）
  3. **Uvicorn のアクセスログ** (`uvicorn.access`): HTTP 通信の記録（例: `GET /health ... 200 OK`）
- **目指す出力イメージ (stdout)**：
  ```text
  2026-09-08 16:30:01 - app.api.v1.health        - INFO - ヘルスチェックが呼ばれました
  2026-09-08 16:30:01 - sqlalchemy.engine.Engine - INFO - SELECT 1
  2026-09-08 16:30:01 - uvicorn.access           - INFO - 127.0.0.1:54321 - "GET /health HTTP/1.1" 200 OK
  ```
- **やること**：
  - `dictConfig`（辞書でログ設定を書く Python 標準のやり方）で設定を1ファイルにまとめる
  - 自分のアプリ用のロガーと、uvicorn のロガーの書式を揃える
  - **SQLAlchemy が発行する SQL をログに出す設定**を、環境変数で切り替えられるようにする（`Settings.sql_echo`）
- **終わったと言える状態**：`/health` を叩くと、アクセスログと `SELECT 1` の両方が同じ形式で出る
- **なぜ今か**：第5段階の N+1 対策で「SQL が何本飛んだか」を数えることになる。
  そのとき使うのがこのログ

#### Step 7. テストの土台を作り、`POST /users` を TDD で書く

- **ねらい**：テストを先に書くループを、最小の題材で回す
- **やること**：
  - テスト用の DB を用意する（本番用と同じ Compose 上に、別のデータベースとして作る）
  - `conftest.py` にフィクスチャを書き、`dependency_overrides` で DB 依存を差し替える
  - テストごとにデータが残らないようにする
  - **失敗するテストを先に書いてから** `POST /users` と `GET /users/{user_id}` を実装する
- **終わったと言える状態**：テストを2回連続で実行しても、両方通る
  （2回目が落ちるなら、前のテストのデータが残っている）
- **つまずきやすい点**：テスト用 DB にもマイグレーションを適用する必要がある。
  「テーブルが無い」エラーの多くはこれ

### 第4段階：関係を1種類ずつ増やす

> 以降の各ステップは、すべて同じ4つの繰り返しになる。
> **モデルを足す → マイグレーションを生成して読む → 適用する → 失敗するテストを書く → 実装する**

#### Step 8. `steps`（順序を持つ1対多）

- **学ぶこと**：行に順序を持たせる方法と、取り出すときの並び替え
- **API**：`POST /recipes` を「手順の配列も一緒に受け取る」形に拡張する
- **終わったと言える状態**：手順を3件つけて登録し、`GET` で 1→2→3 の順に返る

#### Step 9. `ingredients` と `recipe_ingredients`（追加カラムありの多対多）

- **学ぶこと**：association object の書き方。中間テーブルをモデルとして定義する
- **設計上の判断**：材料名が未登録だったらどうするか。
  「エラーにする」「自動でマスタに登録する」のどちらかを**自分で決めて、理由をコメントに残す**
- **終わったと言える状態**：`{"ingredient": "玉ねぎ", "quantity": 200, "unit": "g"}` の形で
  登録でき、取得時にも分量と単位が返る

#### Step 10. `tags` と `recipe_tags`（追加カラムなしの多対多）

- **学ぶこと**：`secondary` を使った書き方。Step 9 との書き分け
- **API**：タグの付け外し2本
- **終わったと言える状態**：同じタグを2回付けても重複行が増えない

- **学ぶこと**：外部キーを主キーにして1対1を DB レベルで保証する方法
- **API**：`PUT /recipes/{recipe_id}/nutrition`（無ければ作る、有れば置き換える）
- **終わったと言える状態**：同じレシピに2回 `PUT` しても行が1つのまま

### 第5段階：読み取り側

#### Step 12. `GET /recipes`（一覧・絞り込み・ページネーション）

- **学ぶこと**：クエリパラメータで条件を組み立てる。件数と明細を返す形の設計
- **やること**：`tag` / `difficulty` / `user_id` / `is_published`（`published_at` の有無による判定）で絞り込む。
  `limit` と `offset`、総件数を返す
- **終わったと言える状態**：条件の組み合わせごとにテストが通る

#### Step 13. N+1 を「測ってから」潰す

- **ねらい**：対策を先に覚えるのではなく、**問題が起きている様子を自分の目で見る**
- **やること**：
  1. Step 6 で入れた SQL ログを有効にして、レシピ10件の一覧を取得する
  2. 発行された SQL の本数を数える（レシピ1本＋関連ごとに10本…と増えているはず）
  3. `selectinload` などで読み込み方を変える
  4. もう一度数える
- **終わったと言える状態**：SQL の本数が件数に比例して増えなくなる。
  可能なら、発行回数をテストで固定する
- **これが今回の山場**：ここまでの設計（関係3種類）が全部この1画面に集まる

### 第6段階：変更と仕上げ

#### Step 14. `PATCH /recipes/{recipe_id}`（部分更新）

- **学ぶこと**：「送られてこなかった項目」と「明示的に `null` を送られた項目」を区別する方法。
  Pydantic でここをどう表現するかが論点

#### Step 15. `DELETE /recipes/{recipe_id}`（削除と連鎖）

- **学ぶこと**：レシピを消したとき、手順・材料の紐付け・栄養情報がどうなるか。
  DB 側の `ON DELETE CASCADE` と ORM 側の `cascade` の違い
- **終わったと言える状態**：削除後に関連テーブルへ孤児の行が残っていないことをテストで確認できる

#### Step 16. 既存データがある状態でのスキーマ変更

- **ねらい**：**今回いちばん実務に近い経験**。空の DB へのマイグレーションとは別物だと知る
- **やること**：`recipes` に「必須の新しい列」を追加する（例：`slug`。URL に使う一意な文字列）
  1. まず「空を許す列」として追加するマイグレーションを書く
  2. 既存の行に値を埋める処理を、同じマイグレーションの中に書く
  3. その後に「空を許さない」制約と一意制約を付ける
- **終わったと言える状態**：既存データが入った DB に対して `upgrade` が成功し、
  `downgrade` で元に戻せる
- **つまずきやすい点**：autogenerate は「いきなり NOT NULL を付ける」マイグレーションを
  生成する。既存行があるとこれは失敗する。**生成されたファイルを手で直す**必要がある

#### Step 17. 仕上げ

- エラーレスポンスの形を全エンドポイントで統一する（前回のやり方を持ち込む）
- ログにリクエストIDを付ける（ミドルウェアで採番し、1リクエストのログを追えるようにする）
- `README.md` に「起動手順」「テスト実行手順」を書く
- 学習まとめを `docs/notes/` に残す

## 8. 実装中に議論する論点

答えを先に決めず、その場面に来たときに考える。

1. **Enum を DB 側でどう表現するか**
   PostgreSQL には専用の ENUM 型がある。一方で「文字列カラム＋Python 側の Enum」で
   済ませる流儀もある。選択肢が増えたときのマイグレーションの手間が分岐点になる。
2. **`source` を JSONB にするのは妥当か**
   出典を検索したくなった瞬間に JSONB は不利になる。列に分けるべきか。
3. **`recipe_ingredients` を複合主キーにするか、`id` を足すか**
   複合主キーは重複を防げるが、この行を単体で指すエンドポイントが作りにくくなる。
4. **削除の連鎖を DB 側でやるか ORM 側でやるか**
5. **テストの分離方式**
   テストごとに全削除するか、トランザクションをロールバックするか。速度と確実さの取引。

## 9. 用語メモ

- **association object**：多対多の中間テーブルに追加の列があるとき、その中間テーブルを
  1つのモデルクラスとして定義するやり方。
- **`secondary`**：追加の列がない中間テーブルを、モデルクラスを作らずに紐付けだけで扱う書き方。
- **N+1 問題**：一覧を取るときに、1件ごとに関連データを取る SQL が追加で飛ぶ現象。
  10件なら 1+10 本、100件なら 1+100 本になり、件数に比例して遅くなる。
- **マイグレーション**：テーブル定義の変更を、履歴として1ファイルずつ残しながら DB に適用する仕組み。
- **ヘルスチェック（Compose）**：コンテナが「起動した」ではなく「使える状態になった」ことを
  判定する設定。DB は起動直後の数秒間、接続を受け付けられない。
- **`dictConfig`**：Python 標準のログ設定を、辞書で一括指定する方式。
- **timestamptz**：タイムゾーン情報つきの日時型（PostgreSQL）。
- **JSONB**：PostgreSQL が JSON を解析済みの形で保存する型。中の項目で検索や索引付けができる。
