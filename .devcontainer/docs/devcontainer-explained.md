# MacBookにおけるDev Container起動の全ステップ

「プロセスの親子関係」や「フロントとバックエンドの分離」、「どのタイミングでコンテナが立ち上がるのか」といった重要なポイントをすべて盛り込んで、MacBook上でDev Containerが立ち上がるまでの一連の流れをステップ形式で解説します。

---

## ステップ1：【事前準備】Docker Desktopの起動（エンジンの待機）

Mac は Linux コンテナをそのままでは動かせません。そこで Docker Desktop は、Mac の中に**小さな Linux マシン（VM）を1台だけ**起動します。以降に作るコンテナは、すべてこの中に住みます。

親子関係は**「画面 → 管理役 → VM」の3階層**です。

```
Docker Desktop.app（画面）         ユーザーが起動するアプリ
└ com.docker.backend（管理役）     常駐して命令を待つ
   └ VM を動かすプロセス           この中でコンテナが動く
```

**この時点でコンテナはまだ0個です。** エンジンをかけて待機しているだけの状態です。

なお、コンテナを実際に作る本体は `dockerd` で、VM の中に存在します。

※ プロセス名はDocker Desktopのバージョンやマシンによって変わります。

---

## ステップ2：VS Codeの起動（ローカルプロセスの展開）

ユーザーがMac上でVS Codeのアプリを開きます。ここで、VS Codeを構成するプロセスが**明確な親子関係**を持って立ち上がります。

- **起きること**
  1. 最初に司令塔となる**「メインプロセス（親）」**が1つだけ起動します。ウィンドウ管理や他プロセスの生成を担います。
  2. メインプロセスが、画面を描画する**「レンダラープロセス（子／フロントエンド）」**を立ち上げます。
  3. 同時に、メインプロセスが、すべての拡張機能の親玉となる**「拡張機能ホストプロセス（子／バックエンド）」**を立ち上げます。

- **ここがポイント**
  これら3つは別々のプロセスですが、**IPC（プロセス間通信）**を使って互いに連絡を取り合い、1つのエディタとして動いています。
  また、インストールされた多くの拡張機能は、JavaScript で書かれており、**この「拡張機能ホスト」という1つのプロセス（同じ部屋）の中で同居して動いています。**（ただし言語サーバー系のプロセスは、拡張機能ホストのサブプロセスとして作られます。そして、これらは Rustなどの言語で作られていることがあります。）
  なお、起動時に全部が読み込まれるわけではありません。多くは Python ファイルを開いた時など、**必要になったタイミングで初めて読み込まれます。**

> **📝 補足：VS Codeのプロセスは3つだけではない**
> 他にも shared process、`ptyHost`（ターミナル管理）、`fileWatcher`（ファイル監視）などが動いています。ここでは主要な3つに絞って説明しています。

## ステップ3：Dev Containerの検知とDockerへの命令（連携の開始）

ユーザーがプロジェクトを開きます。

- **起きること**
  拡張機能ホストの中で動いている「Dev Containers拡張機能（いちプログラム）」が、プロジェクト内の `.devcontainer/devcontainer.json` を見つけ出し、「Reopen in Container」の通知を表示します。ユーザーがそれを選択します。

- **ここがポイント**
  設定を読み取った拡張機能は、Dockerのコマンドラインツールを直接使って、`docker build` や `docker run` を実行します（シェルは経由しません）。これが、ステップ1で待機していたDockerへ連絡（電話）をとる瞬間です。

---

## ステップ4：コンテナの起動と「バックエンド」の送り込み

Mac上のDockerが命令を受け取り、開発用のコンテナが立ち上がります。そして、VS Codeの「フロントとバックエンドが分かれている構造」が最大限に活かされます。

- **起きること**
  1. Dockerが、設定通りにLinuxコンテナを起動します。
  2. **ローカル拡張機能ホストの中で動く「Dev Containers拡張」が、`VS Code Server`（コンテナ内で働く裏方の本体）をまずMac上にダウンロードし、それを named volume（`/vscode`）の仕組みを使ってコンテナへ送り込みます。**
  3. **Mac側から**`docker exec`を打つことで、コンテナ内で VS Code Server が起動し、そのサブプロセスとして**「リモート拡張機能ホスト」**が作られます。
     この`docker exec`が使う実行ユーザーは、`devcontainer.json` の `remoteUser`（未指定なら Dockerfile 最後の `USER` ＝ `containerUser` を継承）で決まります。
  4. なお`docker exec`が打たれるのは、この Server 本体の起動時だけではありません。通信を中継するプロセス用のシェルなど、起動時には複数回の`docker exec`が走ります（本プロジェクトで`ps`を見ると、コンテナ外に親を持つプロセスが5本残っていました）。
  5. Mac側のメインプロセス、レンダラープロセス（画面）、**「ローカル拡張機能ホスト」などは、そのまま残り続けます。**

- **ポイント① ── 拡張機能ホストは「移動」しない**
  ステップ2で立ち上がった拡張機能ホストが丸ごとコンテナへ移動するわけではありません。拡張機能は性質ごとに振り分けられ、**2つの拡張機能ホストが同時に動きます。**

- **ポイント② ── VS Code Server は `PID 1` の子ではない**
  コンテナの `PID 1` は `docker-compose.yml` の `command: sleep infinity` です。VS Code Server は`docker exec`で後から注入された**別のプロセスツリー**です。

**【プロセス配置図】**

```
【Mac 側】

メインプロセス（司令塔）
├ レンダラープロセス（画面／フロントエンド）
└ ローカル拡張機能ホスト
   └ UI系の拡張（テーマ・外観など）
    ※ Dev Containers拡張自身もここに残る


【コンテナ側】

PID 1: sleep infinity（コンテナを生かし続けるだけ）

VS Code Server（裏方の本体／PID 1 の子ではない独立したプロセス）
├ リモート拡張機能ホスト
│  └ ワークスペース拡張（言語系・リンター等）
│     └ 言語サーバーはさらにその子プロセス
├ ptyHost
│  └ ターミナル（zsh）
└ fileWatcher
```

---

## ステップ5：起動完了（エディタの結合）

- **最終状態**
  Mac側に残った「フロントエンド（画面）」と、コンテナ内で新しく立ち上がった「バックエンド（VS Code Server）」が、`docker exec`を通信路として繋がります。

- **通信路の実体**
  VS Code Server はコンテナ内のランダムなポート（実測例: `127.0.0.1:33513`）で待ち受けます。そして`docker exec`で注入された小さな中継プロセスが、標準入出力とそのポートを相互にパイプすることでトンネルが成立します。

---

## まとめ

一見すると「VS Codeを開いてコンテナに入るだけ」のように見えますが、裏側では次のことが行われています。

> **Mac上で待機していたDockerに対し、Mac側の拡張機能ホストで動くDev Containers拡張がコマンドで命令を出し、Mac上でダウンロードした `VS Code Server` を named volume 経由でコンテナへ送り込んで`docker exec`で起動し（実行ユーザーは`remoteUser`）、Macに残った画面（レンダラープロセス）とも`docker exec`で繋ぎ合わせる。**

という、プロセスの分業と結合です。

ポイントは、コンテナへ移るのは**裏方の作業だけ**という点です。画面とUI系の拡張機能はMac側に残り続け、ウィンドウ管理などを担うメインプロセスもMac側から動きません。
